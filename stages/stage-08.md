## 阶段导读

不是所有需求都值得写代码。运营要一个“输入商品就能出三版小红书文案”的工具，你花两周写后端、调模型、做页面，结果需求一周后就变了——这是最常见的技术浪费。这一阶段用 Coze 与 Dify 两个低代码平台，把想法在**小时级**变成可用应用，同时想清楚它们与代码开发的分工边界。

具体要解决四类问题。第一是**知识问答**：把产品手册、售后政策、FAQ 灌进知识库，让机器人答得有依据。第二是**多步任务**：不是单轮聊天，而是“提取参数 → 查库 → 判断 → 生成 → 推送”这样的流程。第三是**内容生产**：卖点、文案、海报提示词、视频脚本，用工作流批量产出。第四是**对外集成**：把应用发布到飞书、钉钉、微信，或者用 API 接进自己的系统。

学完这个阶段，你要能独立完成：搭一个可用的企业知识库、设计带条件分支的工作流、做一个会追问的对话流、用 API 调用平台能力、并把它接进现有业务系统。更重要的是，你要能判断一个需求该用低代码还是该写代码。

最容易踩的坑有六个。**把低代码当万能**：需要复杂权限、私有化、深度定制时，平台会卡死你；**知识库乱分段**：一份 50 页的 PDF 整段切，召回必然不准；**工作流没有兜底分支**：模型输出格式一变，整个流程直接失败；**把令牌写进前端**：等于把账号送人；**只测 happy path**：真实用户会输入空值、错别字、超长文本；**忽视平台限制**：并发、超时、文件大小、渠道审核，每一条都可能让演示翻车。

<div class="callout plain"><span class="tag">大白话</span>
<p>低代码像<b>搭积木</b>：现成的块拼一拼，十分钟出个房子模型，适合先看看“这个想法行不行”。</p>
<p>代码开发像<b>自己烧砖盖房</b>：慢，但想盖几层、想加什么结构都行。</p>
<p>正确姿势是<b>先用积木验证，验证通过再烧砖</b>。反过来最容易返工：花两周写了个没人用的功能。</p>
</div>

## 模块精讲

### 模块1：Coze 平台与知识库

#### 解决什么问题

业务方要一个“懂我们产品”的客服机器人，不能只会闲聊。需要把散落在 PDF、飞书文档、Excel 里的资料变成可检索的知识，再让智能体在回答时引用这些知识，而不是凭模型记忆瞎编。

#### 核心概念

| 概念 | 含义 | 在 Coze 里的位置 |
|-|-|-|
| 资源库 | 统一管理智能体、工作流、知识库、插件 | 左侧导航“资源库” |
| 智能体编排 | 人设、技能、知识、记忆、对话体验五块 | 智能体编辑页 |
| 知识库 | 文档集合，支持文本 / 表格 / 图片 | 资源库 → 知识库 |
| 分段 | 把长文档切成可检索的小块 | 知识库的“分段设置” |
| 召回策略 | 决定每次取回哪些片段 | 知识库或智能体中的召回设置 |
| 插件 | 平台或第三方提供的能力 | 技能 → 插件 |
| 工作流 | 多节点可视化流程 | 资源库 → 工作流 |
| 发布渠道 | 把智能体投放到各端 | 右上角“发布” |
| 个人访问令牌 | 调用 API 的凭证 | 平台设置中的 PAT |

知识库效果的上限由三件事决定：**文档质量、分段方式、召回参数**。文档里全是扫描件图片，解析出来就是乱码；一份 50 页的手册整段切，检索时只能命中一大坨无关内容；Top K 设成 10，上下文被塞满，模型反而抓不住重点。所以搭知识库不是“上传完就完了”，必须做召回测试。

RAG 全链路要完整走一遍：文档解析 → 分段 → 向量化 → 建索引 → 召回 → 重排 → 拼上下文 → 生成。任何一环缺失，回答都会失真；排查时也按这个顺序逐段验证，不要一上来就换模型。

#### 关键实现

搭一个售后政策知识库，按下面的顺序操作：

1. 左侧进入 **资源库**，点 **创建知识库**，选择 **文本格式**，命名为“售后政策库”。
2. 进入知识库后点 **导入数据**，选择 **本地文档**，上传 PDF / Word / Markdown。扫描件先做 OCR，否则解析结果不可用。
3. 打开 **分段设置**：优先选 **自动分段与清洗**；如果文档有清晰标题层级，改用 **自定义分段**，按标题切分，单段控制在 500–800 字，相邻段保留 10%–15% 重叠。
4. 在 **召回测试** 里输入真实用户问题，例如“七天无理由从签收当天算还是发货当天算”，逐条看命中片段。命中片段不含答案就回去改分段，不要急着调模型。
5. 新建智能体，填写名称与简介；在 **人设与回复逻辑** 里写清角色、边界、回答格式。
6. 在 **技能** 区添加需要的插件或工作流；在 **记忆** 区设置变量（如 `user_level`），按需开启长期记忆；在 **对话体验** 里写开场白与快捷指令。
7. 在 **知识** 区域添加刚建的知识库，召回策略选 **混合检索**，Top K 先设 3–5，最小匹配度按测试结果调整。
8. 在右侧 **预览与调试** 里连续问 10 个真实问题，记录答错、答不全、答超纲的情况。
9. 点右上角 **发布**，选择渠道。演示阶段先发 **API**，方便用自己的系统调用。

智能体的人设提示词要写成“约束清单”，而不是一段散文：

```text
# 角色
你是某某品牌的售后客服，只回答售后政策相关问题。

# 知识使用规则
1. 先检索知识库，回答必须基于检索到的内容。
2. 检索不到时，直接说“这个问题我需要转人工确认”，不要猜测。
3. 引用政策时说明出处文档名称，不编造条款编号。

# 输出格式
- 先给结论（一句话）
- 再给依据（引用条款）
- 最后给下一步操作建议

# 禁止
- 不承诺赔偿金额
- 不评价竞品
- 不回答与售后无关的问题
```

用 API 调用已发布的智能体或工作流：

```python
# coze_client.py
import os
import requests

BASE = "https://api.coze.cn"

def run_workflow(user_input: str) -> dict:
    """调用已发布的 Coze 工作流（同步返回）"""
    resp = requests.post(
        f"{BASE}/v1/workflow/run",
        headers={
            "Authorization": f"Bearer {os.getenv('COZE_TOKEN')}",  # PAT 只放服务端
            "Content-Type": "application/json",
        },
        json={
            "workflow_id": os.getenv("COZE_WORKFLOW_ID"),
            "parameters": {"input": user_input},   # 键名必须与工作流入参完全一致
        },
        timeout=60,
    )
    resp.raise_for_status()
    data = resp.json()
    if data.get("code") != 0:                      # 平台业务错误不看 HTTP 状态码
        raise RuntimeError(f"工作流失败：{data.get('msg')}")
    return data

def chat(bot_id: str, user_id: str, question: str) -> dict:
    """调用智能体对话接口（非流式，便于脚本处理）"""
    resp = requests.post(
        f"{BASE}/v3/chat",
        headers={"Authorization": f"Bearer {os.getenv('COZE_TOKEN')}"},
        json={
            "bot_id": bot_id,
            "user_id": user_id,                    # 用于区分会话与计费
            "stream": False,
            "additional_messages": [{"role": "user", "content": question, "content_type": "text"}],
        },
        timeout=60,
    )
    resp.raise_for_status()
    return resp.json()
```

#### 代码解析

| 片段 | 作用 | 为什么这样写 |
|-|-|-|
| `Authorization: Bearer <PAT>` | 身份认证 | 令牌等同账号权限，只能放服务端 |
| `parameters` 的键名 | 映射工作流入参 | 名字对不上会报错或被静默丢弃 |
| `code != 0` 判断 | 识别业务错误 | HTTP 200 也可能是业务失败 |
| `user_id` | 会话隔离 | 同一用户多轮上下文才连得上 |
| `timeout=60` | 超时保护 | 工作流内部可能多次调用模型 |
| `stream: False` | 同步返回 | 脚本与后端代理更好处理 |

#### 常见坑

<div class="callout warn"><span class="tag">易错点</span>
<ul>
<li><b>整份 PDF 直接上传</b>：扫描件没有文字层，解析结果是空的。先 OCR，再检查解析预览。</li>
<li><b>分段过大或过小</b>：2000 字一段召回不准，100 字一段丢上下文。按标题切成 500–800 字最稳。</li>
<li><b>只调模型不调检索</b>：答不准时先看召回片段，八成是没检索到，而不是模型笨。</li>
<li><b>人设写成散文</b>：模型抓不住重点。改成“角色 / 规则 / 格式 / 禁止”四段式清单。</li>
<li><b>令牌写进前端或截图</b>：泄露后别人可以消耗你的额度。定期轮换，按环境分开发/生产令牌。</li>
<li><b>发布前不测边界</b>：空输入、超长输入、无关问题都要测，否则上线第一天就翻车。</li>
</ul>
</div>

### 模块2：Coze 四个电商案例

#### 解决什么问题

电商运营每天重复四件事：想卖点、写文案、做海报、剪视频。每一件都不难，但量大了就压垮人。这四个案例的目标不是“做出惊艳作品”，而是**把重复劳动变成一条可复用的流水线**，并明确哪些环节平台能做、哪些必须人工兜底。

#### 核心概念

| 案例 | 输入 | 核心节点链路 | 输出 |
|-|-|-|-|
| 商品营销海报 | 商品名、卖点、风格、尺寸 | 开始 → 大模型（画面描述）→ 大模型（英文提示词）→ 图像生成 → 结束 | 图片 URL + 说明 |
| 卖点提炼 | 商品标题、详情、评论 | 开始 → 大模型（结构化抽取）→ 代码（去重排序）→ 结束 | 卖点 JSON |
| 小红书文案 | 商品信息、目标人群 | 开始 → 选择器（品类）→ 分支大模型 → 合规检查 → 结束 | 标题 / 正文 / 话题 |
| 商品宣传视频 | 商品信息、时长 | 开始 → 大模型（分镜 JSON）→ 循环 → 图像生成 → 视频生成 → 结束 | 视频 URL 或降级素材 |

四个案例共用一套方法：**先把输出结构定死，再倒推节点**。比如卖点必须是“一句核心 + 三条支撑 + 适用人群”，那就让大模型输出 JSON，用代码节点校验字段，缺字段就重试或降级。反过来先堆节点、最后才想输出，流程一定越改越乱。

#### 关键实现

案例一，海报生成。关键是把“中文卖点”翻译成图像模型能懂的英文画面描述，并且准备兜底分支。

1. 新建工作流，**开始**节点定义 `product_name`、`selling_points`、`style`、`size` 四个输入。
2. 接 **大模型** 节点，提示词要求输出“主体 + 场景 + 光线 + 构图 + 风格”的中文画面描述，不要出现文字。
3. 再接 **大模型** 节点，把描述转成英文提示词，并附负面提示词（如 `text, watermark, logo, low quality`）。
4. 接 **插件** 节点，搜索并添加图像生成类插件，把英文提示词与尺寸传进去。
5. 接 **选择器** 节点：图片 URL 为空走“降级分支”，输出可直接使用的中文文案；不为空走正常结束。
6. **结束** 节点定义 `image_url`、`prompt`、`fallback_text` 三个输出。

案例二，卖点提炼。输出结构如下，直接作为工作流的结束字段：

```json
{
  "core": "一句话核心卖点，20 字以内",
  "points": [
    {"text": "支撑卖点", "reason": "为什么成立", "target": "适用人群"}
  ],
  "price_anchor": "价格锚点描述，没有则留空",
  "risk": ["可能的夸大表述，需要人工复核"]
}
```

提示词里要加三条硬约束：不得出现“最”“第一”“国家级”等绝对化用语；每条卖点必须有详情页或评论中的依据；无法确认的信息写“待确认”，不要编。生成后用代码节点做三件事：去重、截断到 3 条、把 `risk` 非空的结果标记为“需人工审核”。

案例三，小红书文案。用 **选择器** 按品类分流，美妆、食品、家居各用一套人设与禁用词表；最后统一过一个“合规检查”大模型节点，专门挑绝对化用语、医疗功效暗示、虚假折扣。

案例四，宣传视频。先用大模型产出分镜 JSON（每个镜头包含画面、字幕、时长），再用 **循环** 节点逐镜生成图片，最后交给视频生成插件合成。这里必须提前接受一个现实：平台视频插件有时长、分辨率、并发限制，商用前要验证；如果生成失败，降级为“图片序列 + 字幕 + 背景音乐”的模板方案，并在输出里标注 `fallback=true`。

#### 代码解析

| 片段 / 节点 | 作用 | 为什么这样写 |
|-|-|-|
| 开始节点四个入参 | 固定输入契约 | 后期接 API 时参数名不用改 |
| 中文描述 → 英文提示词 | 适配图像模型 | 多数图像模型对英文提示更敏感 |
| 选择器兜底分支 | 处理生成失败 | 插件超时、审核拦截都会返回空 |
| 卖点 JSON 结构 | 让输出可入库 | 结构化才能做校验、去重、排序 |
| `risk` 字段 | 主动暴露风险 | 把合规问题交给人工，而不是藏起来 |
| 循环 + 分镜 | 控制视频生成粒度 | 一次生成整片不可控，分镜可重试 |
| `fallback=true` | 明确降级状态 | 前端据此展示“素材待补”，不假装成功 |

#### 常见坑

<div class="callout warn"><span class="tag">易错点</span>
<ul>
<li><b>让图像模型直接画中文文字</b>：文字基本是糊的。正确做法是生成无字底图，文字后期用设计工具或画布叠加。</li>
<li><b>卖点让模型自由发挥</b>：会写出“全网最低”这类违规表述。必须给禁用词清单并做二次检查。</li>
<li><b>四个案例各建一套工作流</b>：重复劳动。把“商品信息标准化”抽成子工作流复用。</li>
<li><b>视频案例不做失败预案</b>：演示当天插件排队，整场翻车。提前准备图片版降级素材。</li>
<li><b>输出不留痕</b>：不带商品 ID 与生成时间，后面无法追溯是哪版素材。</li>
</ul>
</div>

### 模块3：Dify 平台与工作流

#### 解决什么问题

Coze 上手快，但当你要私有化部署、要把应用嵌进自己的后台、要更细地控制变量与节点时，就需要 Dify。它更像“工程化的 LLM 应用框架”：应用类型分得清、节点更接近编程、API 优先、支持自托管。

#### 核心概念

| 概念 | 含义 | 在 Dify 里的位置 |
|-|-|-|
| 应用类型 | 聊天助手 / 文本生成 / Agent / Chatflow / Workflow | 创建空白应用时选择 |
| 工作流 | 单向流程，适合批处理与报告生成 | Workflow |
| 对话流 | 支持多轮与变量记忆，适合客服 | Chatflow |
| 节点 | 流程中的一步 | 画布左侧节点面板 |
| 变量 | 节点之间传值 | 节点输出 / 变量赋值 |
| 变量聚合器 | 把多个分支结果合并成一个 | 分支汇合处 |
| 知识库 | 文档检索 | 顶部“知识库” |
| 工具 | 内置工具与自定义 OpenAPI 工具 | 顶部“工具” |
| 代码节点 | 写 Python / Node.js 补能力 | 节点面板“代码执行” |
| 发布 | API、WebApp、嵌入网站 | 右上角“发布” |

Workflow 和 Chatflow 的区别要记牢：Workflow 是“一次输入、一次输出”，适合生成报告、批量分析；Chatflow 有会话变量，能记住上一轮说了什么，适合客服与追问。选错类型，后面补记忆会非常别扭。

Dify 的 Agent 应用又是另一种：由模型自主决定调用哪个工具，适合开放式任务。搭建顺序是：创建应用时选 **Agent** → 写指令（角色、可用工具、边界）→ 在工具区添加内置工具或自定义工具 → 设置最大迭代次数防止死循环 → 发布。工具描述越清楚，模型选得越准，这和 Skill 的 description 是同一个道理。

#### 关键实现

搭一个“订单查询”工作流，按下面顺序操作：

1. 顶部 **工作室** → **创建空白应用**，类型选 **Workflow**，命名“订单查询”。
2. **开始** 节点定义输入变量 `order_no`（文本，必填）、`phone_last4`（文本，必填）。
3. 加 **代码执行** 节点，校验单号格式与手机尾号，输出 `valid` 与 `reason`。
4. 加 **条件分支** 节点：`valid` 为假走“参数错误”分支，为真走“查询”分支。
5. 查询分支加 **HTTP 请求** 节点，调用内部订单服务，鉴权信息放环境变量，不写死在节点里。
6. 加 **LLM** 节点，把接口返回的 JSON 转成用户能看懂的话，要求不暴露内部字段。
7. 两个分支都接到 **结束** 节点，分别定义 `answer` 与 `need_retry`。
8. 右上角 **发布**，选 **访问 API**，拿到 API Key 与接口地址。

自定义工具用 OpenAPI Schema 描述，Dify 会自动生成参数表单：

```yaml
# 自定义工具：查询物流轨迹
openapi: 3.0.0
info:
  title: logistics-query
  version: 1.0.0
servers:
  - url: https://api.example.com
paths:
  /track:
    get:
      operationId: queryTrack
      summary: 根据运单号查询物流轨迹
      parameters:
        - name: waybill
          in: query
          required: true
          schema: { type: string }
      responses:
        "200":
          description: 查询成功
          content:
            application/json:
              schema:
                type: object
                properties:
                  status: { type: string }
                  traces:
                    type: array
                    items: { type: string }
```

代码节点适合做“模型不擅长但代码很擅长”的事，比如清洗与统计：

```python
# Dify 代码执行节点（Python3）
import json
import re

def main(comments: str) -> dict:
    """从评论文本中剔除表情与链接，统计负面关键词命中数"""
    text = re.sub(r"https?://\S+", "", comments or "")
    text = re.sub(r"\[.*?\]", "", text)          # 去掉表情占位符
    negatives = ["退货", "假货", "太差", "骗人", "漏发"]
    hits = [w for w in negatives if w in text]
    return {
        "clean_text": text[:1000],
        "neg_hits": hits,
        "neg_count": len(hits),
        "is_negative": len(hits) > 0,
    }
```

#### 代码解析

| 片段 | 作用 | 为什么这样写 |
|-|-|-|
| `Workflow` 而非 `Chatflow` | 一次性查询任务 | 不需要多轮记忆，结构更简单 |
| 代码节点先校验 | 把脏输入挡在外部调用之前 | 省一次接口调用，也避免报错难查 |
| 条件分支两条出口 | 覆盖异常路径 | 没有兜底分支是工作流最常见的线上故障 |
| 鉴权放环境变量 | 防泄露 | 节点配置可能被导出或截图 |
| OpenAPI `operationId` | 工具唯一标识 | 模型按它选择调用哪个工具 |
| 代码节点返回 dict | 供后续节点引用 | 字段名就是变量名，必须稳定 |
| `main(...)` 固定入口 | Dify 的调用约定 | 入口名写错会直接执行失败 |

#### 常见坑

<div class="callout warn"><span class="tag">易错点</span>
<ul>
<li><b>Workflow 里想要多轮记忆</b>：选错类型。需要上下文就建 Chatflow，用会话变量存状态。</li>
<li><b>节点之间变量名不一致</b>：引用到空值，流程静默走错分支。每加一个节点就检查变量引用。</li>
<li><b>条件分支没有默认出口</b>：出现未覆盖的值时流程中断。</li>
<li><b>代码节点里访问外网</b>：沙箱通常不允许，必须改用 HTTP 请求节点。</li>
<li><b>把 API Key 写在节点说明里</b>：导出 DSL 就泄露。统一放环境变量。</li>
<li><b>不装 Rerank 就开混合检索</b>：召回多了但排序乱，回答反而更差。</li>
</ul>
</div>

### 模块4：Dify 四个业务案例

#### 解决什么问题

低代码真正的价值在业务闭环：不只是“生成一段文字”，而是把结果送到该去的地方。这四个案例分别覆盖**分类与工单**、**批量调研**、**对话质检**、**评论洞察**，基本涵盖客服与运营的高频场景。

#### 核心概念

| 案例 | 应用类型 | 关键节点 | 业务产出 |
|-|-|-|-|
| 客户投诉分类（钉钉） | Chatflow | 问题分类器 → 参数提取器 → 条件分支 → 知识检索 → HTTP 请求 | 分类结果 + 钉钉卡片 |
| 一键生成产品调研报告 | Workflow | 迭代 → 搜索工具 → LLM → 变量聚合器 → 模板转换 | Markdown 报告 |
| 客服对话记录分析 | Workflow | 文档提取 → 迭代 → LLM → 代码执行 → LLM | 质检报告 |
| 商品评论分析 | Workflow | 问题分类器 → 参数提取器 → 代码执行 → LLM | 维度评分 + 改进建议 |

四个案例都遵循同一个套路：**先用分类器把问题分流，再用参数提取器拿结构化字段，最后用代码或模板保证输出稳定**。只靠一个大模型节点做完全部事情，结果一定不稳定。

#### 关键实现

案例一，投诉分类并推送到钉钉：

1. 新建 **Chatflow**，**开始** 节点接收用户消息。
2. 加 **问题分类器**，类别设为“物流、质量、退款、其他”，每类给两条示例。
3. 加 **参数提取器**，从用户话里抽 `order_no`、`phone`、`demand` 三个字段，设为必填。
4. 加 **条件分支**：字段缺失走“追问”分支，用 **直接回复** 让用户补充；字段齐全走“处理”分支。
5. 处理分支加 **知识检索** 查对应品类的处理 SOP，再接 **LLM** 生成回复。
6. 加 **HTTP 请求** 节点调用钉钉自定义机器人 Webhook，把分类、单号、摘要拼成 Markdown 消息。
7. **结束** 节点输出回复文本与工单 JSON。

钉钉机器人要先在群里配置：群设置 → 智能群助手 → 添加机器人 → 自定义 → 安全设置选“加签”或“自定义关键词” → 复制 Webhook 地址。请求体格式如下：

```json
{
  "msgtype": "markdown",
  "markdown": {
    "title": "新投诉工单",
    "text": "### 新投诉工单\n- 分类：物流\n- 单号：SF123456\n- 诉求：要求今天送达\n- 情绪：负向\n\n请相关同事 30 分钟内响应。"
  }
}
```

如果用“加签”模式，需要在代码节点里计算签名：

```python
# Dify 代码执行节点：生成钉钉加签参数
import base64
import hashlib
import hmac
import time
import urllib.parse

def main(secret: str) -> dict:
    timestamp = str(round(time.time() * 1000))
    string_to_sign = f"{timestamp}\n{secret}"
    h = hmac.new(secret.encode(), string_to_sign.encode(), hashlib.sha256).digest()
    sign = urllib.parse.quote_plus(base64.b64encode(h))
    return {"timestamp": timestamp, "sign": sign}
```

案例二，调研报告。用 **迭代** 节点遍历竞品列表，每个竞品走“搜索工具 → LLM 摘要”，结果汇入 **变量聚合器**，最后用 **模板转换** 拼成固定结构的 Markdown，再交给一个 LLM 做整体结论。注意迭代节点的并发要设小一点，否则容易触发搜索工具限流。

案例三，客服记录分析。先用 **文档提取** 读取上传的对话文件，按会话切分后迭代，每个会话让 LLM 判断意图、情绪、是否合规；代码节点统计各维度占比；最后一个 LLM 基于统计结果写改进建议。不要让一个 LLM 直接读 500 条对话，上下文会爆。

案例四，评论分析。问题分类器把评论分成好评、差评、咨询；参数提取器抽出“质量、物流、价格、服务”四个维度的评分（1–5）；代码节点算均分与差评率；LLM 结合典型评论写改进建议。输出的评分表可以直接进周报。

#### 代码解析

| 片段 | 作用 | 为什么这样写 |
|-|-|-|
| 问题分类器 | 先分流再处理 | 不同类别用不同提示词，准确率更高 |
| 参数提取器设为必填 | 保证工单完整 | 缺单号无法处理，必须先追问 |
| 条件分支“追问”出口 | 把缺失信息补全 | 比让模型猜单号靠谱得多 |
| 钉钉 Markdown 消息 | 群里可读 | 纯文本在手机上很难扫读 |
| 加签计算 | 通过钉钉安全校验 | 只配关键词容易被伪造消息 |
| 迭代 + 聚合 | 批量处理不爆上下文 | 每个竞品独立总结，最后再合并 |
| 代码节点统计 | 数字交给代码 | 模型算百分比经常出错 |

#### 常见坑

<div class="callout warn"><span class="tag">易错点</span>
<ul>
<li><b>分类器类别太多</b>：十几个类别互相重叠，准确率骤降。先控制在 4–6 类，不够再加二级分类。</li>
<li><b>直接让模型生成钉钉 JSON</b>：少个引号就发送失败。用模板或代码拼装。</li>
<li><b>迭代节点并发拉满</b>：搜索工具直接限流。并发设 2–3，并加失败重试。</li>
<li><b>把整份对话塞给一个 LLM</b>：上下文超限且结论笼统。先切分再汇总。</li>
<li><b>不记录原始输入</b>：分类错了无法复盘。日志里保留输入与分类结果。</li>
<li><b>忽略钉钉频率限制</b>：每分钟消息数有上限，批量推送要限速并合并。</li>
</ul>
</div>

## 综合实战

### 实战目标

从零做一个**对外可用的客服分析应用**：用户在网页提交一段客服对话，Dify 完成意图识别、情绪判断、合规检查与改进建议，结果通过后端代理返回，同时把高风险工单推送到钉钉群。整条链路覆盖知识库、工作流、代码节点、API、后端代理与监控。

### 第 1 步：在 Dify 建知识库

1. 顶部 **知识库** → **创建知识库**，命名“客服话术与合规规范”。
2. 数据源选 **导入已有文本**，上传话术手册与合规文档。
3. 分段选 **通用分段**，最大长度 600，重叠 80；索引选 **高质量**。
4. 检索设置选 **混合检索**，开启 Rerank，Top K 设 4。
5. 用 10 个真实问题做召回测试，命中率低于 80% 就回去改分段。

### 第 2 步：建 Workflow

1. **工作室** → **创建空白应用** → **Workflow**，命名“客服对话质检”。
2. **开始** 节点定义 `dialog_text`（段落，必填）、`agent_name`（文本）。
3. 加 **LLM** 节点“意图与情绪”：输出 JSON，字段为 `intent`、`emotion`、`emotion_score`。
4. 加 **知识检索** 节点，查询词用 `intent`，挂第 1 步的知识库。
5. 加 **LLM** 节点“合规检查”：输入对话与检索到的规范，输出 `violations` 数组。
6. 加 **代码执行** 节点：校验 JSON 字段、计算风险分、生成工单号。
7. 加 **条件分支**：风险分大于 70 走“高危”分支，否则走“常规”分支。
8. 两个分支都接 **结束**，输出 `report`、`risk_score`、`ticket_no`。
9. 右上角 **发布** → **访问 API**，记录 API Key。

### 第 3 步：写后端代理

前端绝不能直接拿 Dify 的 Key。后端负责鉴权、限流、日志与错误兜底：

```python
# server.py
import os
import requests
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel

app = FastAPI()
DIFY_URL = "https://api.dify.ai/v1/workflows/run"
DIFY_KEY = os.getenv("DIFY_API_KEY")          # 只存在服务端环境变量

class Req(BaseModel):
    dialog_text: str
    agent_name: str = "unknown"

@app.post("/api/qc")
def qc(req: Req):
    if len(req.dialog_text) < 20:
        raise HTTPException(400, "对话内容太短")
    resp = requests.post(
        DIFY_URL,
        headers={"Authorization": f"Bearer {DIFY_KEY}"},
        json={
            "inputs": {"dialog_text": req.dialog_text, "agent_name": req.agent_name},
            "response_mode": "blocking",       # 长流程可改 streaming 走 SSE
            "user": "web-" + req.agent_name,   # 用于区分调用来源
        },
        timeout=120,
    )
    if resp.status_code != 200:
        raise HTTPException(502, f"工作流调用失败：{resp.text[:200]}")
    data = resp.json()
    return data.get("data", {}).get("outputs", {})
```

### 第 4 步：推送到钉钉并留痕

在高危分支后加 **HTTP 请求** 节点调用钉钉 Webhook；同时在后端把 `ticket_no`、`risk_score`、耗时写入日志表。监控看三个指标：调用成功率、P95 耗时、高危工单占比。任何一个异常升高，先查 Dify 的工作流日志，看是模型超时还是工具限流。

### 解析表

| 步骤 | 关键动作 | 验收信号 |
|-|-|-|
| 知识库 | 分段 600 字 + 混合检索 + Rerank | 召回测试命中率 ≥ 80% |
| 意图情绪 | 强制 JSON 输出 | 10 条样本字段齐全 |
| 合规检查 | 输入对话 + 规范片段 | violations 能指到具体条款 |
| 代码校验 | 字段校验 + 风险分 + 工单号 | 非法输出被拦截并降级 |
| 条件分支 | 高危 / 常规两条出口 | 两条都能走到结束 |
| 发布 API | 拿到 Key 与地址 | Postman 调用返回 outputs |
| 后端代理 | 鉴权 + 超时 + 错误兜底 | 前端看不到 Key |
| 钉钉推送 | 加签 + Markdown 卡片 | 群内 3 秒内收到 |
| 监控 | 成功率 / P95 / 高危占比 | 有看板或至少日志可查 |

<div class="callout tip"><span class="tag">老师建议</span>
<p>演示时准备三段输入：一段正常、一段情绪激烈、一段缺关键信息。第三段最能体现你的条件分支与追问设计，评委通常就看这个。</p>
</div>

## 疑难点分级

| 知识点 | 难度 | 典型卡点 | 破解方式 |
|-|-|-|-|
| 知识库分段 | 中 | 召回片段不含答案 | 按标题切 500–800 字 + 重叠，先做召回测试 |
| 混合检索与 Rerank | 高 | 召回多但排序乱 | 开 Rerank，Top K 控制在 4–6 |
| 人设提示词 | 中 | 回答跑题、爱编造 | 四段式清单 + 强制“检索不到就说不知道” |
| 工作流变量传递 | 中 | 下游拿到空值 | 每个节点检查引用名，改完立刻试运行 |
| 条件分支完整性 | 中 | 分支覆盖不全导致中断 | 画流程图，补默认分支 |
| 代码节点边界 | 高 | 访问外网、依赖缺失 | 只用标准库，外部请求改走 HTTP 节点 |
| Coze / Dify 选型 | 中 | 选完发现不支持私有化 | 先列硬性要求再打分，别只看演示效果 |
| 平台锁定 | 高 | 想迁走发现流程无法导出 | 核心逻辑与提示词留在自己仓库 |
| API 鉴权 | 高 | Key 泄露、被刷额度 | 后端代理 + 环境变量 + 定期轮换 |
| 长流程超时 | 高 | 网关 60 秒断开 | 异步任务 + 轮询或 SSE |
| 渠道发布审核 | 中 | 发布被驳回 | 提前读渠道规范，去掉绝对化用语 |
| 钉钉加签 | 中 | 机器人返回 310000 | 时间戳 + 密钥 HMAC + URL 编码 |
| 迭代节点限流 | 高 | 搜索工具 429 | 并发降到 2–3 + 重试 + 缓存 |
| 输出结构稳定性 | 高 | 模型少字段导致入库失败 | JSON 模式 + 代码校验 + 重试一次 |
| 应用可观测性 | 中 | 出错不知道哪一步 | 平台日志 + 自建调用日志 + 告警 |
| 平台配额 | 中 | 演示当天额度用完 | 提前估算调用量，准备备用账号 |

## 阶段项目

### 项目一：Coze 电商营销应用

**背景**：某家居店铺每周上新 20 个 SKU，运营要手写卖点、文案与海报提示词，平均每个商品 40 分钟。目标是压缩到 5 分钟以内，并保证不出现违规表述。

**功能清单**：

- 输入商品标题、详情、三条用户评论
- 输出核心卖点、三条支撑卖点、适用人群
- 输出小红书标题、正文、5–8 个话题标签
- 输出海报画面描述与英文提示词
- 合规检查：绝对化用语、功效暗示、虚假折扣
- 支持一键发布到 API，供内部工具调用

**技术选型**：Coze 工作流（大模型 + 代码节点 + 选择器 + 图像生成插件）+ Python 后端代理。

**验收标准**：

| 验收项 | 标准 |
|-|-|
| 结构化输出 | 卖点 JSON 字段完整率 100% |
| 合规性 | 50 条生成结果中零绝对化用语 |
| 稳定性 | 连续调用 30 次，失败率低于 5% |
| 可用性 | 单商品处理时间不超过 90 秒 |
| 可追溯 | 每次输出带商品 ID 与生成时间 |

**评分点**：工作流设计 25 分，提示词质量 25 分，合规检查 20 分，失败兜底 15 分，API 集成 15 分。

### 项目二：Dify 客服分析应用

**背景**：客服团队每天产生 800 段对话，主管只能抽查 20 段，无法及时发现态度问题与合规风险。需要一个自动质检系统，并把高危工单实时推给组长。

**功能清单**：

## 常见面试题

### 问题 1：什么需求适合低代码，什么必须写代码？

要点：验证性需求、内部工具、标准问答与内容生成，适合低代码，几小时能上线；涉及复杂权限、私有化、超大规模并发、深度定制算法、与多个内部系统强耦合时，必须写代码。判断标准不是“难不难”，而是“是否需要平台之外的控制权”。

### 问题 2：知识库召回不准，你的排查顺序是什么？

要点：先看召回测试命中片段是否含答案——不含，是分段或解析问题；含但排在后面，是排序问题，调 Top K、最小匹配度、加 Rerank；含且排前但模型仍答错，才是提示词或模型问题。顺序不能反，否则会一直在调模型上浪费时间。

### 问题 3：Coze 和 Dify 怎么选？

要点：Coze 强在渠道发布与开箱即用的插件，适合快速验证、面向 C 端或社媒场景；Dify 强在节点粒度、API 优先、可私有化，适合企业内部系统集成。数据敏感选可自托管的 Dify；要快速发到飞书、微信选 Coze。最好两个都做一遍再定。

### 问题 4：工作流节点和代码函数怎么对应？

要点：开始/结束对应入参与返回值，LLM 对应一次模型调用，知识检索对应向量检索，条件分支对应 if/else，代码节点对应普通函数，HTTP 请求对应 `requests`。理解映射后，任何代码流程都能翻译成工作流，迁移成本大幅下降。

### 问题 5：工作流为什么必须设计兜底分支？

要点：模型输出格式会漂移、插件会超时、检索可能为空。没有兜底分支，任何一个异常都会让流程中断且难以定位。兜底分支要做三件事：给出可用的降级结果、记录失败原因、通知相关人员。

### 问题 6：平台令牌怎么管理才安全？

要点：只放服务端环境变量，不入库、不进前端、不截图；按环境区分开发与生产令牌；设置最小权限与额度上限；定期轮换；所有调用经过后端代理，代理层做鉴权、限流和日志。

### 问题 7：Workflow 和 Chatflow 的区别？

要点：Workflow 是一次输入一次输出，无会话状态，适合报告生成、批量分析；Chatflow 有会话变量，能记住多轮上下文，适合客服与追问。选错的代价是后期补记忆非常别扭。

### 问题 8：低代码应用的性能瓶颈通常在哪？

要点：模型调用耗时、外部工具限流、平台并发配额、网关超时。优化手段：减少不必要的模型节点、合并重复调用、加缓存、把长任务改成异步、把批量任务拆小并控制并发。

### 问题 9：怎么避免被低代码平台绑定？

要点：提示词、知识库原文、业务规则、评测集都放在自己的仓库；核心数据处理放在自己的服务里；平台只承担编排与模型调用；对外只暴露自己的 API，不让业务系统直连平台。

### 问题 10：第三方工具接入要注意什么？

要点：鉴权方式（API Key / OAuth）、超时与重试、错误码映射、返回结构稳定性、调用配额。用 OpenAPI Schema 描述清楚参数与返回，模型才能正确选择工具；不要依赖对方返回的自然语言描述。

### 问题 11：低代码应用上线后怎么监控？

要点：至少四项：调用成功率、P95 耗时、模型 token 消耗、业务指标（如高危工单占比）。平台日志只能看单次调用，业务指标要自己在代理层记录。出现异常先定位是模型、工具还是网络。

## 阶段小结

- 低代码适合验证需求与内部工具，核心业务仍建议代码开发；先积木后烧砖，返工最少。
- 知识库效果由文档质量、分段方式、召回参数三者决定，模型不是第一嫌疑人。
- 工作流节点本质是函数，理解映射关系就能在平台与代码之间自由翻译。
- 每个工作流都要有兜底分支，异常路径比正常路径更值得设计。
- 对外集成必须走后端代理，令牌只放服务端，日志里也不能出现。
- Workflow 管一次性任务，Chatflow 管多轮对话，选型错了后面很难补。
- 平台会变，能力要沉淀：提示词、规则、评测集放自己仓库，别只存在平台里。

下一阶段进入 Vibe Coding：不再依赖可视化平台，用自然语言驱动 AI 完成一个完整全栈项目的交付，并把能力封装成可复用的 Skill。
