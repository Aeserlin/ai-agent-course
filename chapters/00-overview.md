## 本章导读

欢迎来到 AI Agent 全能开发的第一课。这一章几乎不写复杂业务代码，目标只有一个：**在你的脑子里装一张地图**。

很多同学学完十几章 RAG、LangChain、MCP，依然说不清“我这套东西到底算不算 Agent”。原因不是代码写得少，而是缺一张概念地图：不知道边界在哪，就不知道该往哪个方向堆功能，最后做出来的是一个“会调大模型的定时脚本”，却对外宣称是 Agent。

这一章会把三件事讲透：第一，Agent 的判定标准是什么，什么样的系统只是“套壳聊天”；第二，一个 Agent 由哪五个零件组成，每个零件坏掉会在线上表现成什么故障；第三，Agent、RAG、工作流、普通脚本这四者到底怎么选，选错了会多花多少冤枉钱。

学完本章，你应该能做到：拿到一个需求，先用 3 分钟判断它该做成工作流还是 Agent；能画出自己项目的五大零件图；能在新机器上 15 分钟内把环境配好并跑通连通性验证。

初学者在本章最容易踩的五个误区，先提前打预防针：

1. **把“调用了大模型”当成 Agent。** 判据不是有没有模型，而是步骤由谁决定：写死在代码里的是工作流，模型临场决定下一步的才是 Agent。
2. **一上来就做全能 Agent。** 开放式 Agent 的调试成本是工作流的 3～5 倍，先跑稳流程再放开自主性，是性价比最高的路径。
3. **把记忆理解成“模型自带的记忆”。** 模型的记忆就是你每次请求发过去的那个 `messages` 数组，服务端不保存你的上下文，不传就等于失忆。
4. **密钥写进代码再推到 Git。** 公开仓库里的 `sk-` 密钥平均几分钟内就会被爬虫扫走，账单可能一夜之间多出几百美元。
5. **忽略超时与重试。** 默认不设超时会让你在演示现场卡住 3 分钟以上，而一次网络抖动就足以毁掉整场 Demo。

<div class="callout plain"><span class="tag">大白话</span>
<p>把这一章想成<b>装修前的量房</b>：你还没买瓷砖（写业务代码），但必须先知道承重墙在哪（概念边界）、水电怎么走（五大零件）、预算多少（成本模型）。</p>
<p>量房花 1 小时，能省掉后面砸墙重做的 3 天。这一章就是那 1 小时。</p>
</div>

## Agent 到底是什么

先给一个不严谨但极其有用的定义：

> **Agent = 能自己决定“下一步做什么”的程序。**

普通程序是你写死步骤：先 A，再 B，最后 C。Agent 不一样，你只给它目标和工具，它自己规划顺序、自己判断要不要再试一次、自己决定什么时候停下来。

这个定义的实操价值在于：它给了你一把尺子。拿到任何“AI 应用”的需求，问一句——**下一步做什么，是代码里的 if-else 决定的，还是模型在运行时决定的？** 答案决定你该用工作流还是 Agent，也决定了你的测试策略、成本模型和故障处理方式。

<div class="callout plain"><span class="tag">大白话</span>
<p>把大模型想象成一个<b>能力很强但刚入职的实习生</b>。</p>
<p>你问他“帮我查下明天北京天气”，他能答，但他<b>没有手</b>——不能真的打开浏览器；也<b>没有记忆</b>——聊完就忘。</p>
<p>Agent 就是给这个实习生配上：一台电脑（工具）、一个笔记本（记忆）、一份工作流程（编排）。于是他从“会聊天”变成“会办事”。</p>
</div>

### 五大零件

| 零件 | 作用 | 常见实现 | 坏了会怎样 |
|-|-|-|-|
| 大脑 | 理解目标、做决策 | 大语言模型（LLM） | 答非所问、乱调工具 |
| 手 | 与外部世界交互 | 工具 / Function Calling / MCP | 只会说不会做 |
| 记忆 | 记住上下文与历史 | 对话历史、向量库 | 反复问同样的问题 |
| 眼睛 | 读取外部知识 | RAG、检索、文件读取 | 一本正经地胡说 |
| 流程 | 控制循环与协作 | ReAct、状态图、多 Agent | 死循环、任务做一半就停 |

请记住这张表。后面每一章，本质上都是在强化其中一个零件：第 3 章强化“手”的输出格式，第 5 章强化“眼睛”，第 6 章强化“流程”，第 8 章同时强化五个零件的工程化。

### 每个零件对应的概念

| 概念 | 一句话解释 | 在本项目里的影子 |
|-|-|-|
| LLM（大语言模型） | 根据上文预测下一个 Token 的模型，是 Agent 的决策核心 | 所有 `client.chat.completions.create` 调用 |
| 工具调用 | 模型输出“我要调哪个函数、参数是什么”，由你的代码真正执行 | `tools` 参数与 `tool_calls` 字段 |
| 规划 | 把大目标拆成有序子任务的能力，通常靠提示词或外层循环实现 | `max_steps` 循环、任务清单提示词 |
| ReAct | 思考（Reason）与行动（Act）交替进行的经典循环范式 | 第 4 章的 Agent 主循环 |
| MCP | 模型上下文协议，用统一接口把外部工具接进模型 | 第 7 章的工具接入 |
| 无状态服务 | 服务端不保存会话，状态全靠客户端传入 | 必须自己维护 `messages` |

### 三个判定问题

不确定手上的系统算不算 Agent，连续问三个问题：

1. **步骤是谁定的？** 代码里写死的 `if/else` 就是工作流；模型运行时输出“下一步调哪个工具”的才是 Agent。
2. **有没有闭环？** 工具返回结果后，模型会不会基于结果再决策一次？只会调一次工具然后汇总的，通常还是工作流。
3. **失败了会不会自救？** 工具报错后，模型能不能换参数重试或换工具，是 Agent 与脚本的关键分水岭。

三个问题都答“是”，才算一个完整的 Agent。少一个，建议先按工作流做，稳定后再升级。

## Agent、RAG、工作流有什么区别

初学者最容易把这三个概念混在一起。用一句话区分：

- **工作流（Workflow）**：路径是人画好的，模型只在节点内干活。
- **RAG**：给模型外挂一个“资料库”，解决“不知道”的问题。
- **Agent**：路径由模型自己决定，解决“不会做多步任务”的问题。

| 对比项 | 普通脚本 | 工作流 | RAG | Agent |
|-|-|-|-|-|
| 步骤由谁决定 | 程序员 | 程序员 | 程序员 | 模型 |
| 能否调外部工具 | 可以 | 可以 | 一般不需要 | 核心能力 |
| 适合任务 | 固定流程 | 流程稳定但内容多变 | 知识问答 | 开放式多步任务 |
| 主要风险 | 不灵活 | 难以覆盖异常 | 检索不准 | 死循环、成本失控 |
| 单次成本量级 | 几乎为 0 | 1 次模型调用 | 1 次检索 + 1 次模型调用 | 3～15 次模型调用 |
| 典型调试耗时 | 低 | 低到中 | 中（召回率难调） | 高（行为不确定） |

### 用一个例子讲清三者

需求：用户发来一张报销单截图，要求判断是否符合公司差旅标准，并生成审批意见。

- **普通脚本**：写死规则，金额小于 500 元直接通过。规则一改就要发版，遇到“住宿费超了但机票省了”就判不了。
- **工作流**：先 OCR 抽字段，再查差旅标准库，再让模型写审批意见，最后人工确认。路径固定，每步可单测，出错能定位到具体节点。
- **RAG**：把公司差旅制度切成 300～500 字的片段存进向量库，提问时召回最相关的 3 条，让模型照制度回答。解决“制度文件有 80 页，模型没看过”的问题。
- **Agent**：模型自己决定先查制度、再查历史同类单据、发现金额异常时调用汇率工具，最后给出意见。适合“每次判断路径都可能不同”的复杂场景。

| 概念 | 一句话解释 | 在本项目里的影子 |
|-|-|-|
| 工作流编排 | 人预先画好节点与连线，模型只填内容 | 第 4 章的链式调用示例 |
| 检索增强生成 | 先检索相关资料，再把资料塞进提示词 | 第 5 章的向量检索 |
| 自主决策 | 模型根据中间结果选择下一个动作 | 第 4 章的 ReAct 循环 |
| 编排框架 | 用状态图或图结构管理工作流与 Agent | 第 6 章的多 Agent 协作 |

<div class="callout plain"><span class="tag">大白话</span>
<p>工作流像<b>地铁</b>：轨道铺好了，车只能沿线走，准点、便宜、好维护。</p>
<p>Agent 像<b>网约车</b>：司机自己选路，能绕开堵点，但可能绕远、可能加价。</p>
<p>RAG 像<b>给司机配了一本当地地图册</b>：他不认识的地方，翻书就知道。三者不是互斥关系，而是可以叠加的三种能力。</p>
</div>

<div class="callout tip"><span class="tag">老师建议</span>
<p>不要一上来就做“全能 Agent”。先做<b>工作流</b>，把流程跑稳；发现某几步确实需要模型临场判断，再把那一段升级成 Agent。这个顺序能帮你省掉大量调试时间，也让上线时间提前 1～2 周。</p>
</div>

## 环境准备

本项目使用 Python 3.11 与 OpenAI 兼容接口。国内可直接使用任意兼容 OpenAI 协议的服务商，把 `base_url` 换掉即可，代码一行不用改。

### 安装依赖

```bash
python --version                                    # 1. 确认版本，必须是 3.10 以上
python -m venv .venv                                # 2. 创建虚拟环境，避免污染全局
.venv\Scripts\Activate.ps1                          # 3. Windows 激活
source .venv/bin/activate                           # 4. macOS 或 Linux 激活
pip install "openai>=1.0" python-dotenv httpx       # 5. 安装核心依赖
python -c "import openai; print(openai.__version__)"   # 6. 验证，应输出 1.x
```

如果 PowerShell 提示“禁止运行脚本”，执行一次 `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`，再重新激活。

### 配置密钥

在项目根目录新建 `.env` 文件，**不要提交到 Git**：

```bash
OPENAI_API_KEY=sk-你的密钥                     # 密钥，仅保存在本地
OPENAI_BASE_URL=https://api.openai.com/v1      # 兼容协议的服务地址
MODEL_NAME=gpt-4o-mini                         # 默认模型
```

同时在 `.gitignore` 里加一行 `.env`。判断是否漏配的方法：在终端执行 `git status`，如果看到 `.env` 出现在待提交列表里，立刻把它移出暂存区。

### 连通性测试

```python
import os
from dotenv import load_dotenv
from openai import OpenAI

load_dotenv()   # 1. 读取 .env 中的配置，加载到环境变量

#---- 2. 创建客户端：base_url 决定你连哪家服务 ----
client = OpenAI(
    api_key=os.getenv("OPENAI_API_KEY"),      # 密钥，只从环境变量取，绝不写死
    base_url=os.getenv("OPENAI_BASE_URL"),    # 兼容 OpenAI 协议的服务地址
    timeout=30,                               # 超时时间，防止请求一直挂着
)

resp = client.chat.completions.create(   # 3. 发一条最小请求，确认链路通畅
    model=os.getenv("MODEL_NAME", "gpt-4o-mini"),
    messages=[{"role": "user", "content": "用一句话解释什么是 AI Agent"}],
)

print(resp.choices[0].message.content)          # 4. 打印模型回复
print("输入 Token：", resp.usage.prompt_tokens)   # 5. 打印用量，确认不是空响应
print("输出 Token：", resp.usage.completion_tokens)
```

### 代码解析

| 片段 | 作用 | 为什么这样写 |
|-|-|-|
| `load_dotenv()` | 读取 `.env` | 密钥与代码分离，改配置不用改代码 |
| `api_key=os.getenv(...)` | 从环境变量取密钥 | 避免密钥进入版本库，也方便在服务器上用环境变量覆盖 |
| `base_url` | 指定服务地址 | 兼容协议的服务商可无缝切换，只改这一行 |
| `timeout=30` | 设置超时 | 没有超时，网络抖动会让程序永久卡住 |
| `messages` | 对话消息数组 | 这是所有多轮对话与 Agent 的基础数据结构 |
| `usage.prompt_tokens` | 输入 Token 数 | 成本核算的唯一可靠来源，估算永远有偏差 |

<div class="callout warn"><span class="tag">易错点</span>
<ul>
<li><b>密钥写进代码</b>：一旦推到公开仓库，几分钟内就会被扫走盗刷。</li>
<li><b>忘记激活虚拟环境</b>：装到了全局 Python，换项目就冲突。</li>
<li><b>base_url 漏写 /v1</b>：大多数兼容服务要求带 <code>/v1</code> 后缀，否则返回 404。</li>
<li><b>把 Key 尾部空格复制进去</b>：报 401，但看起来密钥完全正确，极难排查。</li>
<li><b>用 Python 3.9 运行</b>：部分新版 SDK 的类型注解会直接报语法错误。</li>
</ul>
</div>

## 代码实操：跑通一个最小 Agent 循环

连通性测试只证明“能聊天”。下面这段代码才第一次让你的程序具备“手”：模型自己决定是否调用工具、调用哪个工具、参数填什么。

```python
import json
import os
from dotenv import load_dotenv
from openai import OpenAI

load_dotenv()
client = OpenAI(
    api_key=os.getenv("OPENAI_API_KEY"),
    base_url=os.getenv("OPENAI_BASE_URL"),
    timeout=60,
)
MODEL = os.getenv("MODEL_NAME", "gpt-4o-mini")

#---- 1. 工具“说明书”：告诉模型有这个工具、它干什么、要什么参数 ----
TOOLS = [{
    "type": "function",
    "function": {
        "name": "get_weather",
        "description": "查询指定城市当天的天气，返回温度和天气状况",
        "parameters": {
            "type": "object",
            "properties": {
                "city": {"type": "string", "description": "城市中文名，例如 北京"}
            },
            "required": ["city"],
        },
    },
}]

def get_weather(city: str) -> str:
    """工具的真实实现。教学用假数据，避免依赖外部网络。"""
    fake = {"北京": "晴，18 摄氏度", "上海": "小雨，22 摄氏度"}
    return fake.get(city, f"暂无 {city} 的数据")

TOOL_IMPL = {"get_weather": get_weather}

def run_agent(question: str, max_steps: int = 5) -> str:
    messages = [
        {"role": "system", "content": "你是一个助手。需要外部信息时必须调用工具，禁止编造。"},
        {"role": "user", "content": question},
    ]

    for step in range(max_steps):
        # 2. 每轮都带上完整历史与工具清单
        resp = client.chat.completions.create(
            model=MODEL,
            messages=messages,
            tools=TOOLS,
            temperature=0,          # 工具调用必须稳定，温度压到 0
        )
        msg = resp.choices[0].message

        # 3. 关键：assistant 这条消息（含 tool_calls）必须回写
        messages.append(msg.model_dump(exclude_none=True))

        # 4. 没有工具调用，说明模型已经能直接回答，循环结束
        if not msg.tool_calls:
            return msg.content or ""

        # 5. 有工具调用，就逐个真实执行，并把结果作为 tool 消息回写
        for call in msg.tool_calls:
            args = json.loads(call.function.arguments or "{}")
            result = TOOL_IMPL[call.function.name](**args)
            print(f"[第 {step + 1} 步] 调用 {call.function.name}，参数 {args}，结果 {result}")
            messages.append({
                "role": "tool",
                "tool_call_id": call.id,   # 必须与请求的 id 一致
                "content": result,
            })

    # 6. 兜底：超过步数就强制停止，防止死循环烧钱
    return "已达到最大步数，任务未完成，请缩小问题范围"

if __name__ == "__main__":
    print(run_agent("北京和上海今天天气怎么样？我需要决定穿什么"))
```

#### 代码解析

| 片段 | 作用 | 为什么这样写 |
|-|-|-|
| `TOOLS` 里的 `description` | 让模型知道何时该用它 | 描述写得越像“使用场景”，误调用越少；只写“查询天气”准确率约 70%，写清“查指定城市当天天气”可到 90% 以上 |
| `temperature=0` | 降低随机性 | 工具名和 JSON 参数必须稳定，0.7 以上会偶发参数拼错 |
| `msg.model_dump(...)` | 把模型回复转成可回写的字典 | 不回写这条，下一轮模型不知道自己刚才请求过工具，会重复调用 |
| `tool_call_id` | 关联请求与结果 | 不一致会被服务端拒绝，报 400 |
| `max_steps=5` | 限制循环次数 | 典型任务 2～4 步完成，5 步是安全上限 |
| `print` 日志 | 观察决策过程 | Agent 调试的核心手段就是看它每一步在干嘛 |

<div class="callout warn"><span class="tag">易错点</span>
<ul>
<li><b>只把工具结果拼进文本</b>而不按 <code>role="tool"</code> 回写，模型会以为工具没被调用，反复请求。</li>
<li><b>不设 <code>max_steps</code></b>：工具一直返回“暂无数据”，模型就会一直重试，一晚烧掉几十元。</li>
<li><b>工具函数抛异常没捕获</b>：整个循环崩掉。正确做法是捕获后把错误信息作为 tool 结果回写，让模型自己换个思路。</li>
<li><b>工具描述写成内部术语</b>：例如“调用 CRM 的 v2 接口”，模型不知道什么时候该用，永远不调用。</li>
</ul>

## 综合案例：会议纪要整理 Agent

把本章知识串成一个真实场景：运营同学每天有 3～5 场会，需要把录音转写文本整理成固定格式的纪要，并同步到知识库。

**输入**：一段 2000～8000 字的会议转写文本，包含多人发言、口语填充词、偶尔的错别字。

**流程**：

1. 判断文本长度，超过 6000 字先分段，每段 3000 字左右，避免超出上下文。
2. 第一轮调用：抽取结构化信息，输出 JSON，字段为议题、结论、待办、负责人、截止时间。
3. 第二轮调用：把 JSON 渲染成中文纪要，固定为“结论先行 + 待办列表”。
4. 校验：待办里有负责人但没有截止时间的，标记为“待确认”，不直接入库。
5. 入库：调用知识库写入工具，返回文档链接。

**输出**：一份 300～500 字的纪要 + 一个可点击的文档链接 + 一条“3 条待办中有 1 条待确认”的提示。

**失败处理**：

| 失败点 | 表现 | 处理策略 |
|-|-|-|
| 转写文本过长 | 请求报上下文超限 | 先分段，再对分段结果做二次汇总 |
| 模型输出不是合法 JSON | `json.loads` 抛异常 | 用低温度重试 1 次，仍失败则降级为纯文本纪要 |
| 字段缺失 | 没有负责人字段 | 填“待确认”，不阻断流程，人工补齐 |
| 知识库写入失败 | 接口返回 500 | 本地落盘为 Markdown，并记录失败队列，5 分钟后重试 |
| 内容涉及敏感信息 | 命中手机号、身份证规则 | 脱敏后再入库，同时提示“已脱敏 2 处” |

<div class="callout plain"><span class="tag">大白话</span>
<p>这个案例里，真正决定成败的不是模型多聪明，而是<b>你有没有想清楚每一步失败了怎么办</b>。</p>
<p>凡是能自动跑的东西，一定会自动出错。区别只在于：你提前写了兜底，还是半夜被电话叫醒。</p>
</div>

<div class="callout tip"><span class="tag">老师建议</span>
<p>这个案例我建议先用<b>工作流</b>实现（三步固定），跑 50 份真实纪要统计准确率；只有当“是否需要查历史会议”这类判断频繁出现时，再把第 1 步升级为 Agent。先测再改，比一开始就上 Agent 省 70% 的调试时间。</p>
</div>

## 疑难点分级

| 知识点 | 难度 | 典型卡点 | 破解方式 |
|-|-|-|-|
| Agent 与工作流的边界 | 中 | 觉得“用了大模型就是 Agent” | 问自己：步骤是我写死的，还是模型临场定的？ |
| 五大零件的对应关系 | 低 | 概念记住了但不会用 | 每写一段代码，标注它属于哪个零件 |
| 无状态与上下文 | 中 | 以为服务端会记住对话 | 记住：记忆等于你传的 `messages` 数组 |
| 工具调用协议 | 高 | 不知道 `tool_calls` 与 `role="tool"` 怎么配对 | 手写一遍最小循环，打印每一步的 messages |
| 工具描述撰写 | 中 | 模型该调不调、不该调乱调 | 描述写清“什么时候用”，并给 1 个参数示例 |
| OpenAI 兼容协议 | 低 | 换服务商就报错 | 只改 `base_url` 和 `model`，其余不动 |
| 环境隔离 | 低 | 包冲突、版本混乱 | 每个项目一个 `.venv` |
| 密钥管理 | 低 | 提交到 Git 导致盗刷 | `.env` 加 `.gitignore`，并设消费上限 |
| 超时与重试 | 中 | 网络抖动导致程序卡死 | `timeout` 设 30～60 秒，重试 2 次并指数退避 |
| 死循环控制 | 中 | Agent 反复调同一个工具 | 设 `max_steps`，并在提示词里要求“同一工具最多调 2 次” |
| 成本预估 | 中 | 上线后账单超预期 5 倍 | 按“调用次数 × 输入长度”做公式估算，再加 30% 冗余 |
| 流式与工具调用共存 | 高 | 流式时拿不到完整 tool_calls | 工具调用阶段不开流式，或手动拼接增量 |
| 多轮状态管理 | 中 | 多用户串话 | 按会话 ID 隔离 messages，禁止用全局列表 |
| 可观测性 | 高 | 线上出问题无法复现 | 记录每轮的输入、输出、工具参数与耗时 |
| 选型判断 | 中 | 简单需求也上 Agent | 用三个判定问题过一遍，能工作流就工作流 |

## 常见面试题

| 问题 | 考察点 | 答题要点 |
|-|-|-|
| 你怎么定义 AI Agent？ | 概念边界 | Agent 是能自主决定下一步动作的程序，核心是“决策权在模型”；与工作流的区别是路径由谁生成，不是有没有用大模型。 |
| Agent 由哪些部分组成？ | 架构认知 | 大脑（LLM）、手（工具）、记忆（上下文与向量库）、眼睛（RAG）、流程（循环与编排）五部分；缺“手”只会说，缺“流程”会中途停。 |
| 工作流和 Agent 怎么选？ | 工程取舍 | 流程稳定优先工作流，调试成本约为 Agent 的三分之一；只在“分支无法穷举”时引入 Agent，通常能省 50% 以上维护成本。 |
| RAG 能解决什么问题，不能解决什么？ | 技术边界 | 解决“知识不在模型参数里”；不能解决多步推理与工具操作，也不能修复检索质量差导致的幻觉。 |
| Function Calling 的原理是什么？ | 底层机制 | 模型不执行函数，只输出结构化 JSON（函数名 + 参数）；由应用侧解析并真正执行，再把结果作为 `tool` 消息回传。 |
| 为什么必须回写 assistant 的 tool_calls 消息？ | 协议细节 | 服务端无状态，不回写模型就不知道自己请求过工具，会重复调用或直接报 400。 |
| 如何防止 Agent 死循环？ | 稳定性 | 设最大步数（常用 5～10）、同工具调用次数上限（2～3 次）、总 Token 预算上限，任一触顶即中止并返回兜底话术。 |
| 工具描述怎么写才准？ | 提示工程 | 写清“何时使用 + 输入含义 + 1 个参数示例”，误调用率可从 30% 降到 10% 以内。 |
| 怎么估算一次 Agent 任务的成本？ | 成本意识 | 成本约等于调用轮数 × 单轮输入 Token × 单价；一个 4 步 Agent 的输入成本常是单次问答的 6～10 倍。 |
| 国内如何接入 OpenAI 协议？ | 落地能力 | 选兼容服务商，改 `base_url` 与 `model`，SDK 与代码不变；注意部分服务对 `tools` 支持程度不同，需实测。 |
| Agent 上线前必须做哪些防护？ | 生产意识 | 密钥隔离、消费上限、超时重试、循环上限、敏感信息脱敏、全链路日志，缺一项都可能造成事故。 |
| 为什么建议先工作流后 Agent？ | 经验判断 | 工作流每步可单测、可回放；Agent 行为不确定，排障要 3 倍时间。先稳定后自主，是成本最低的演进路径。 |

## 本章小结

- Agent 的本质是**让模型自己决定下一步**，判据是决策权归属，而不是有没有调用大模型。
- 五大零件：大脑、手、记忆、眼睛、流程。后续每一章都在强化其中之一。
- 工作流、RAG、Agent 不是替代关系，而是三种可叠加的能力；先用工作流跑稳，再局部升级为 Agent。
- 模型服务是无状态的，**记忆等于你每次发过去的 `messages`**，不传就是失忆。
- 工具调用是“模型出 JSON、你的代码干活、结果再回传”的三段式，`tool_call_id` 必须严格配对。
- 环境上做到四件事：虚拟环境隔离、密钥进 `.env`、请求设超时、循环设上限。
- 成本意识要第一天建立：调用轮数乘以输入长度，才是真实账单的量级。
- 上线前先想失败：每个自动化步骤都要有降级路径和兜底话术。

下一章我们正式进入“大脑”的细节：Token、上下文窗口、温度，这些参数会直接决定你 Agent 的稳定性与成本。
