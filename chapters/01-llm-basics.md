## 本章导读

这一章解决一个非常实际的问题：**为什么同一个问题，模型有时答得好、有时答得糟？**

答案通常不在“模型不行”，而在你没搞懂四个参数：Token、上下文窗口、温度、最大输出长度。搞懂它们，你才能控制成本、稳定输出、避免“聊到一半突然失忆”。

先给一组真实数字建立痛感：一个客服 Agent，如果每轮都把完整历史发过去，第 20 轮的输入可能是第 1 轮的 8 倍；一个把温度设成 1.2 的抽取任务，同一个订单号会被解析成三种格式；一个没设 `max_tokens` 的总结功能，单次输出 4000 字，成本直接翻 5 倍。这些都不是模型的问题，是参数的问题。

学完本章，你应该能做到：用 `usage` 精确算出一次对话花了多少钱；用“预算制”而不是“感觉”来裁剪历史；知道什么任务该用 0 度、什么任务该用 0.8 度；能写出既支持多轮又支持流式的对话函数，并在长会话中自动压缩。

初学者在本章最容易踩的五个误区：

1. **以为 Token 等于字数。** 中文大约 1 个字 1 个 Token，英文约 4 个字符 1 个 Token，代码和 JSON 因为符号多，往往比中文更费 Token。
2. **认为只有输出才计费。** 输入同样计费，而且长对话里输入的累计量往往远大于输出，通常占总成本的 70% 以上。
3. **把上下文窗口当成“可用长度”。** 128K 是输入加输出的总和上限，你还要给输出留位置，实际可用输入建议不超过窗口的 60%～70%。
4. **温度越高越“聪明”。** 温度只改变随机性，不改变知识量；做抽取、工具调用、分类时高温度只会让结果不可复现。
5. **只调 `max_tokens` 不做裁剪。** 限制输出能省钱，但长会话真正的成本大头是输入历史，不裁剪等于没优化。

<div class="callout plain"><span class="tag">大白话</span>
<p>把模型想成一辆<b>按里程计价的出租车</b>：Token 是里程，上下文窗口是后备箱容量，温度是司机的“随性程度”，<code>max_tokens</code> 是你说的“最多开 10 公里就停”。</p>
<p>你要做的不是换一辆更贵的车，而是<b>别让后备箱里堆满没用的旧行李</b>。</p>
</div>

## Token：模型的“计费单位”

模型不是按“字”处理文本，而是按 **Token**。一个 Token 大约等于 0.5～1 个汉字，英文约 4 个字符。不同模型的切词器不同，所以同一段话在不同模型上的 Token 数可能差 15%～30%。

| 内容类型 | 粗略换算 | 1000 Token 大约等于 |
|-|-|-|
| 简体中文正文 | 1 字约 0.7～1 Token | 1000～1400 字 |
| 英文单词 | 1 词约 1.3 Token | 约 750 个单词 |
| 代码 | 1 行约 8～15 Token | 约 80～120 行 |
| JSON 数据 | 1 个字段约 5～10 Token | 约 120～200 个字段 |

<div class="callout plain"><span class="tag">大白话</span>
<p>把 Token 想成<b>出租车的计价里程</b>。你上车说目的地（输入），车开过去（输出），最后按里程收费。</p>
<p>所以：<b>聊天记录越长，每次对话越贵</b>。因为每一轮你都要把之前的完整历史重新发给模型。</p>
</div>

### 成本陷阱

假设第一轮对话历史是 500 Token，之后每轮增加 200 Token，你聊了 20 轮。很多人以为总消耗是 20 乘 500 等于 10000 Token，实际不是：第 1 轮输入 500，第 2 轮 700，第 20 轮约 4300，累计输入约 20 乘 (500 + 4300) 除以 2，约 48000 Token。**是“不保留历史”方案的 4.8 倍。**

| 方案 | 20 轮累计输入 Token | 相对成本 |
|-|-|-|
| 每轮不带历史（单轮问答） | 约 10000 | 1.0 倍 |
| 每轮带完整历史 | 约 48000 | 4.8 倍 |
| 只保留最近 6 条 | 约 18000 | 1.8 倍 |
| 最近 6 条 + 历史摘要 | 约 22000 | 2.2 倍 |

以某轻量模型每百万输入 Token 0.15 美元计，48000 Token 约 0.0072 美元，看似很少；但如果这是一个每天 5000 次会话的线上客服，单日输入成本就是 36 美元，一个月超过 1000 美元。**量级一变，参数就是钱。**

这就是为什么长对话的 Agent 必须做“历史压缩”或“摘要”。

### 成本计算公式

```python
#---- 成本估算：不需要联网，改数字就能算 ----
INPUT_PRICE = 0.15    # 每百万输入 Token 的美元价，按服务商公示填写
OUTPUT_PRICE = 0.60   # 每百万输出 Token 的美元价

def cost_of(prompt_tokens: int, completion_tokens: int) -> float:
    """返回一次请求的美元成本，保留 6 位小数"""
    return (prompt_tokens / 1_000_000) * INPUT_PRICE + \
           (completion_tokens / 1_000_000) * OUTPUT_PRICE

def project_daily_cost(rounds: int, avg_prompt: int, avg_completion: int, sessions: int) -> float:
    """按“每次会话轮数 × 单轮平均用量 × 每日会话数”估算日成本"""
    one_session = rounds * cost_of(avg_prompt, avg_completion)
    return one_session * sessions

#---- 场景：每次会话 10 轮，每轮输入 2000 Token、输出 300 Token，每天 5000 次会话 ----
print(round(project_daily_cost(10, 2000, 300, 5000), 2), "美元/天")
```

<div class="callout warn"><span class="tag">易错点</span>
<ul>
<li>拿“输出单价”估总价：多数场景输入量是输出的 5～10 倍，只看输出会低估成本。</li>
<li>忘记缓存命中价：部分服务商对重复前缀有折扣，但只有把稳定内容放前面才可能命中。</li>
<li>用估算值对账：报销与预算必须用 <code>usage</code> 的真实数字，估算只用于设计阶段。</li>
</ul>
</div>

## 上下文窗口：模型的“短期记忆”

每个模型都有上下文上限（常见 8K、32K、128K、200K Token）。超过就会被截断或直接报错。关键认知：**窗口是输入加输出的总和**，不是只给输入的。

| 现象 | 真实原因 | 解决方向 |
|-|-|-|
| 聊到后面忘了开头 | 早期消息被截断 | 摘要压缩、只保留关键信息 |
| 贴长文档报错 | 超出上下文窗口 | 分段处理 / RAG |
| 回答越来越慢 | 输入 Token 越来越多 | 精简历史、减少冗余 |
| 回答开始“跳读” | 长上下文中部信息利用率下降 | 把关键内容放开头或结尾，减少无关段落 |

| 窗口大小 | 中文可用输入估算 | 约等于 | 适用场景 |
|-|-|-|-|
| 8K | 5000～7000 字 | 5～8 页文档 | 单轮问答、分类抽取 |
| 32K | 2 万～2.5 万字 | 20～25 页 | 单篇长文总结 |
| 128K | 8 万～9 万字 | 80～100 页 | 多文档对比、代码仓库问答 |
| 200K | 13 万～15 万字 | 130～180 页 | 超长报告、整本手册 |

实践建议：**把可用预算压到窗口的 60% 左右**。比如 128K 的模型，输入控制在 8 万 Token 以内，留出输出空间与安全余量。经验上，输入超过窗口 80% 后，模型对中段信息的召回率会明显下降，回答质量反而不如“少给一点、给准一点”。

## 温度与采样参数

| 参数 | 作用 | 建议值 |
|-|-|-|
| `temperature` | 随机性，越高越发散 | 事实类 0～0.3，创意类 0.7～1.0 |
| `top_p` | 采样范围，控制候选词集合 | 一般保持默认，不与 temperature 同时调 |
| `max_tokens` | 最大输出长度 | 按任务设定，防止话痨烧钱 |
| `frequency_penalty` | 降低重复用词 | 长文本生成时可加，0.3～0.8 |
| `presence_penalty` | 鼓励引入新话题 | 头脑风暴时 0.3～0.6 |
| `seed` | 尽力让结果可复现 | 评测与回归测试时固定 |

温度对不同任务的实际影响，用同一句提示词跑 10 次的结果来对照：

| 温度 | 同一抽取任务的结果一致性 | 适合的任务 |
|-|-|-|
| 0 | 10 次结果基本完全一致 | 工具调用、JSON 抽取、分类、审核 |
| 0.3 | 9 次一致，措辞略有差异 | 技术问答、代码生成 |
| 0.7 | 4～6 次结构相同、表达不同 | 文案改写、教学讲解 |
| 1.0 | 2～3 次结构相同 | 头脑风暴、创意标题 |
| 1.5 | 结果可能逻辑断裂、跑题 | 不建议在业务中使用 |

<div class="callout tip"><span class="tag">老师建议</span>
<p>做 Agent 时，<b>工具调用与结构化输出一律用低温度</b>（0～0.2）。你需要的是稳定和可解析，不是文采。判断标准很简单：如果这段输出要被代码 <code>json.loads</code> 解析，温度就必须是 0。</p>
</div>

<div class="callout plain"><span class="tag">大白话</span>
<p>温度就像<b>点菜时的“随便程度”</b>。温度 0 是“照菜单点”，每次都一样；温度 1 是“让厨师自由发挥”，可能惊喜也可能踩雷。</p>
<p>请客户吃饭（生产环境）别让厨师自由发挥，自己吃饭（创意草稿）可以随便一点。</p>
</div>

## 模型怎么选：一张可执行的对照表

选型不是选“最强”，而是选“够用且便宜”。判断顺序：先看任务是否需要复杂推理，再看上下文长度，最后看延迟与价格。

| 场景 | 推荐档位 | 理由 | 温度 | 单轮成本参考 |
|-|-|-|-|-|
| 分类、打标、情感判断 | 小模型 | 任务简单，大模型提升有限，成本差 10～30 倍 | 0 | 极低 |
| 结构化抽取（JSON） | 小模型 + 严格提示 | 小模型在明确 schema 下准确率可达 95% 以上 | 0 | 极低 |
| 技术问答、代码生成 | 中档模型 | 需要一定推理与代码能力 | 0.2～0.4 | 中 |
| 多步 Agent 规划 | 中高档模型 | 规划错误会连锁放大，省这点钱不划算 | 0～0.3 | 中高 |
| 长文档理解（8 万字以上） | 长上下文模型 | 窗口不够就只能分段，效果与成本都变差 | 0.2 | 高 |
| 创意文案、起名 | 中档模型 + 高温度 | 需要多样性，不需要最强推理 | 0.8～1.0 | 中 |

一条可落地的策略：**主力用中档模型，简单任务路由到小模型，疑难问题升级到大模型**。实测中，这种分层路由通常能省 40%～60% 成本，而端到端效果只下降 2%～5%。

路由用代码实现只要十几行，核心是先做一次廉价判断，再决定用哪个模型：

```python
#---- 分层路由：按问题复杂度选择模型与温度 ----
SMALL_MODEL = "gpt-4o-mini"     # 便宜，适合分类与抽取
LARGE_MODEL = "gpt-4o"          # 更贵，适合多步推理

def route(question: str) -> tuple:
    """返回 (模型名, 温度)。规则可替换成小模型分类，成本更低"""
    simple_keys = ["分类", "打标", "抽取", "翻译", "总结一句话"]
    hard_keys = ["为什么", "方案", "对比", "设计", "推理", "多步"]

    if len(question) < 60 and any(k in question for k in simple_keys):
        return SMALL_MODEL, 0.0
    if any(k in question for k in hard_keys):
        return LARGE_MODEL, 0.3
    return SMALL_MODEL, 0.2

if __name__ == "__main__":
    for q in ["把这句话翻译成英文", "为什么我的 Agent 会陷入死循环，给我一个改造方案"]:
        print(q, "->", route(q))
```

注意：路由本身不要再用一次大模型调用，否则省下的钱又被路由吃掉。用关键词或小模型做路由，单次成本要低于主调用的 5%。

## 实操一：多轮对话 + 流式输出

```python
import os
from dotenv import load_dotenv
from openai import OpenAI

load_dotenv()
client = OpenAI(
    api_key=os.getenv("OPENAI_API_KEY"),
    base_url=os.getenv("OPENAI_BASE_URL"),
    timeout=60,
)

MODEL = os.getenv("MODEL_NAME", "gpt-4o-mini")

#---- 对话历史：所有消息都放在这个列表里 ----
messages = [
    {"role": "system", "content": "你是一位严谨的 Python 讲师，回答要简洁、给例子。"}
]

def chat(user_input: str) -> str:
    """发送一轮对话并返回完整回复"""
    # 1. 先把用户这句话加入历史
    messages.append({"role": "user", "content": user_input})

    # 2. stream=True 表示流式返回，边生成边打印
    stream = client.chat.completions.create(
        model=MODEL,
        messages=messages,
        temperature=0.3,     # 教学场景要稳定，温度调低
        max_tokens=800,      # 限制输出长度，控制成本
        stream=True,
    )

    collected = []           # 用来累积完整回复，最后回写历史
    for chunk in stream:
        delta = chunk.choices[0].delta
        # 有些服务首个 chunk 没有 content，必须判空
        piece = delta.content or ""
        if piece:
            print(piece, end="", flush=True)
            collected.append(piece)

    print()  # 换行
    answer = "".join(collected)

    # 3. 关键：把模型回复也写回历史，下一轮才能"记得"
    messages.append({"role": "assistant", "content": answer})
    return answer


if __name__ == "__main__":
    chat("什么是列表推导式？")
    chat("那它和生成器有什么区别？")   # 能正确指代"它"，说明上下文生效
```

#### 代码解析

| 片段 | 作用 | 为什么这样写 |
|-|-|-|
| `messages` 列表 | 承载完整对话 | 模型的记忆就是这个数组，没有它就没有多轮 |
| `append(user)` | 记录用户输入 | 顺序很重要：先入历史再请求，顺序反了模型会漏掉本轮问题 |
| `stream=True` | 流式输出 | 首字延迟通常从 1.5 秒降到 0.3 秒，体感差异巨大 |
| `delta.content or ""` | 容错 | 首个 chunk 常为空，不判空会抛 `TypeError` |
| `"".join(collected)` | 拼接完整文本 | 直接用 `+=` 拼字符串在长文本下会明显变慢 |
| `append(assistant)` | 回写模型回复 | 漏了这步，模型下一轮就“失忆”，指代类问题必然答错 |

<div class="callout warn"><span class="tag">易错点</span>
<ul>
<li>只 append 用户消息、不 append 模型消息 —— 最常见的新手 bug。</li>
<li>把 <code>temperature</code> 设成 1.5，然后抱怨输出不稳定。</li>
<li>长对话不做裁剪，最后 Context 超限报错。</li>
<li>流式输出时用 <code>chunk.choices[0].message</code>：流式返回的是 <code>delta</code>，取错字段会一直拿到 None。</li>
<li>把 <code>messages</code> 定义成全局变量做多用户服务：所有用户会串到同一个会话里。</li>
</ul>
</div>

## 实操二：Token 预算与历史压缩

真实项目里不能等报错才处理。正确做法是每轮请求前先算预算，超了就压缩。下面这段代码实现“保留 system、保留最近 6 条、把更早的对话压成一段摘要”。

```python
import os
from dotenv import load_dotenv
from openai import OpenAI

load_dotenv()
client = OpenAI(
    api_key=os.getenv("OPENAI_API_KEY"),
    base_url=os.getenv("OPENAI_BASE_URL"),
    timeout=60,
)
MODEL = os.getenv("MODEL_NAME", "gpt-4o-mini")

MAX_INPUT_TOKENS = 3000   # 自定预算，远低于模型上限，给输出留空间
KEEP_RECENT = 6           # 最近保留的完整消息条数

def estimate_tokens(text: str) -> int:
    """保守估算：中文按 1 字 1 Token，其余按 4 字符 1 Token"""
    zh = sum(1 for ch in text if "\u4e00" <= ch <= "\u9fff")
    return int(zh + (len(text) - zh) / 4) + 1

def total_tokens(msgs: list) -> int:
    """消息本身有格式开销，每条额外算 4 个 Token"""
    return sum(estimate_tokens(m.get("content") or "") for m in msgs) + 4 * len(msgs)

def summarize(old: list) -> str:
    """把早期对话压成不超过 150 字的摘要"""
    text = "\n".join(f"{m['role']}: {m['content']}" for m in old)
    resp = client.chat.completions.create(
        model=MODEL,
        messages=[
            {"role": "system", "content": "你是对话摘要器。用不超过 150 字总结关键事实、用户偏好与未完成事项，只陈述，不评论。"},
            {"role": "user", "content": text},
        ],
        temperature=0,       # 摘要必须稳定
        max_tokens=200,
    )
    return resp.choices[0].message.content or ""

def fit_budget(msgs: list) -> list:
    """返回一个不超过预算的新消息列表，不修改原列表"""
    if total_tokens(msgs) <= MAX_INPUT_TOKENS:
        return msgs

    system = [m for m in msgs if m["role"] == "system"]
    dialog = [m for m in msgs if m["role"] != "system"]
    old, recent = dialog[:-KEEP_RECENT], dialog[-KEEP_RECENT:]

    summary = summarize(old) if old else ""
    result = system + recent
    if summary:
        result = system + [{"role": "system", "content": f"【历史摘要】{summary}"}] + recent
    return result


if __name__ == "__main__":
    history = [{"role": "system", "content": "你是电商客服，回答简短。"}]
    for i in range(12):
        history.append({"role": "user", "content": f"第 {i} 个问题：" + "我想咨询订单物流。" * 20})
        history.append({"role": "assistant", "content": "已为您记录，请提供订单号。" * 10})

    before = total_tokens(history)
    fitted = fit_budget(history)
    print("压缩前：", before, "Token")
    print("压缩后：", total_tokens(fitted), "Token")
    print("消息条数：", len(history), "->", len(fitted))
```

#### 代码解析

| 片段 | 作用 | 为什么这样写 |
|-|-|-|
| `estimate_tokens` | 本地快速估算 | 避免每轮多一次 API 调用；估算偏保守，宁可多裁一点 |
| `+ 4 * len(msgs)` | 计算消息格式开销 | 每条消息的 role 与分隔符也计费，长会话里这部分不可忽略 |
| `old[:-KEEP_RECENT]` | 切分旧消息与近期消息 | 近期消息承载当前语境，必须完整保留 |
| `summarize(old)` | 压缩历史 | 150 字摘要约 150 Token，替代上千 Token 的原文，压缩比常达 5～10 倍 |
| 返回新列表 | 不修改入参 | 原始历史仍可用于审计与回放，避免“压缩后再也找不到原话” |
| `temperature=0` | 摘要稳定 | 摘要会被反复引用，措辞漂移会导致后续回答前后矛盾 |

<div class="callout tip"><span class="tag">老师建议</span>
<p>裁剪策略不要只用“最近 N 条”。更稳的组合是：固定保留 system、保留最近 6 条、把“用户姓名、订单号、已确认结论”这类关键事实单独抽成一个 <code>facts</code> 字典长期携带。实测这种“摘要 + 关键事实”的方案，比纯滑动窗口的任务完成率高约 25%。</p>
</div>

## 综合案例：长会话客服机器人

**输入**：用户连续咨询订单，30 轮内可能涉及 3 个订单、2 次改地址、1 次退款申请。

**流程**：

1. 每轮进入前先跑 `fit_budget`，输入控制在 3000 Token 以内。
2. 首轮抽取并保存结构化事实：订单号、商品、用户诉求，存入 `facts` 字典。
3. 每轮把 `facts` 以一段固定文本放入 system，保证关键信息不因裁剪丢失。
4. 调用模型时温度 0.2，`max_tokens` 300，保证回答简短且稳定。
5. 每轮结束打印 `usage`，累计超过单会话预算（例如 0.02 美元）时提示转人工。

**输出**：一段 100 字以内的回答，加一条内部日志，记录本轮的输入 Token、输出 Token、是否触发裁剪。

**失败处理**：

| 失败点 | 表现 | 处理策略 |
|-|-|-|
| 摘要调用失败 | 接口超时 | 跳过摘要，改用“只保留最近 6 条”的降级策略 |
| 摘要丢关键信息 | 用户重复报订单号 | 用 `facts` 兜底，并在提示词里要求“不确定时反问” |
| 累计成本超预算 | 单会话超过 0.02 美元 | 停止自动回答，输出转人工提示 |
| 用户情绪激烈 | 出现投诉关键词 | 提高优先级，直接转人工，不再走模型 |
| 历史含敏感信息 | 手机号、地址 | 入历史前脱敏，日志中只留后 4 位 |

<div class="callout plain"><span class="tag">大白话</span>
<p>长会话管理的本质是<b>“带一个笔记本开会”</b>：不用记住每一句话，但要记住结论、待办和人名。摘要就是会议纪要，<code>facts</code> 就是会后行动项。</p>
<p>只带录音（完整历史）太重，只带脑子（不裁剪）会忘，纪要加行动项才是工程解。</p>
</div>

## 疑难点分级

| 知识点 | 难度 | 典型卡点 | 破解方式 |
|-|-|-|-|
| Token 与成本的关系 | 中 | 不知道钱花在哪 | 打印 `resp.usage` 看输入/输出 Token |

| 历史重复计费 | 中 | 以为只算增量 | 画一张 20 轮的累计曲线，看清平方级增长 |
| 上下文窗口 | 中 | 以为模型“记性差” | 理解历史被截断，主动做摘要 |
| 窗口预留 | 中 | 输入塞满导致输出被截断 | 输入控制在窗口 60% 左右 |
| 流式输出的增量拼接 | 中 | 拼出来的文本缺字 | 只截取 `delta.content`，判空后累积 |
| 流式与工具调用 | 高 | 流式下拿不到完整参数 | 工具阶段关闭流式，或手动拼接增量 JSON |

| 成本超预算 | 中 | 上线后账单失控 | 设单会话与单日预算，超限降级 |

| 模型选型 | 中 | 一律用最强模型 | 分层路由：小模型打底、大模型兜底 |

## 常见面试题

| 问题 | 考察点 | 答题要点 |
|-|-|-|
| Token 是什么，中文怎么换算？ | 基础概念 | 模型的最小处理单位；中文约 1 字 1 Token，英文约 4 字符 1 Token，代码与 JSON 更费 Token。 |
| 为什么长对话成本会超线性增长？ | 成本模型 | 每轮都重发完整历史，第 N 轮输入约等于前 N 轮之和，累计量呈平方级增长；20 轮可达单轮的 4～5 倍。 |
| 输入和输出哪个更贵？ | 计费结构 | 单价上输出通常是输入的 3～5 倍；但总量上输入常是输出的 5～10 倍，所以输入往往占总成本 70% 以上。 |
| 上下文窗口超限会怎样？ | 机制理解 | 多数服务直接报 400；部分实现会静默截断早期消息，表现为“忘记开头”，比报错更难排查。 |
| 如何设计历史裁剪策略？ | 工程能力 | 固定 system + 最近 6 条 + 早期摘要 + 结构化 facts；按 Token 预算触发，而不是按条数。 |
| temperature 和 top_p 的区别？ | 采样参数 | 温度整体缩放概率分布，top_p 截断候选集合；同时调会叠加随机性，工程上只调一个。 |
| 什么任务必须用 0 度？ | 实践判断 | 工具调用、JSON 抽取、分类、审核、任何要被代码解析的输出。 |
| 流式输出怎么实现？ | 编码能力 | `stream=True`，遍历 chunk 取 `delta.content` 并判空累积，最后一次性回写历史。 |
| 流式能拿到 usage 吗？ | 细节 | 需要显式开启流式用量返回（部分服务支持），否则只能本地估算。 |
| 如何让输出可复现？ | 稳定性 | 温度 0、固定 `seed`（若支持）、固定提示词与模型版本；即便如此也只能做到“基本一致”。 |
| 模型选型的判断顺序？ | 架构能力 | 先看任务复杂度，再看上下文长度，最后看延迟与单价；简单任务路由到小模型可省 40%～60%。 |
| 摘要会丢信息，怎么补？ | 方案设计 | 摘要只保留结论，关键实体单独结构化存储；提示词要求“信息不足时反问而不是猜”。 |

## 本章小结

- Token 是计费单位，历史会重复计费，长对话必须压缩；20 轮完整历史的成本约是单轮的 4～5 倍。
- 中文约 1 字 1 Token，代码与 JSON 更费；估算只用于设计，对账只信 `usage`。
- 上下文窗口是输入加输出的总和，实际输入建议控制在窗口的 60% 左右。
- 温度控制随机性：要做解析就压到 0，要多样性才放到 0.7 以上。
- `top_p` 与温度只调一个，两个一起调会让行为不可控、难以复现。
- 多轮对话的关键是**同时回写用户与模型的消息**，顺序错、漏写都会导致失忆。
- 历史管理用“固定 system + 最近 6 条 + 摘要 + 关键事实”，比单纯滑动窗口稳。
- 模型选型分层：小模型打底、中档主力、大模型兜底，通常能省一半成本。
